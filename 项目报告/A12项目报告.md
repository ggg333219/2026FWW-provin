## 2. 系统架构与工程规模

### 2.1 三层服务架构

| 层 | 技术栈 | 源码位置 | 职责 |
|---|---|---|---|
| 前端 | Vue 3 + Pinia + Vue Router | `frontend/teacher/` | 教师端工作台，9 个页面 |

**跨层调用原则**（来源：`文档/000-README.md`「跨层原则」）：

- 层隔离：Agent Orchestrator（Go）分发任务，Skill 逻辑在 AI Engine（Python），Skill 间不直接调用
- 默认异步：解析/生成/导出走 Redis 队列，API 立即返回 `task_id`，前端轮询
- 工具复用：上传、文档解析、视频解析、OCR、索引为共享工具层
- 证据协议：每次生成调用接收 `evidence_packet`，输出携带 `citation_refs[]`
- 版本边界：Skill 产生内容，版本模块负责快照

### 3.1 意图理解与状态机（C-01）— ✅ 已实现

**追问字段优先级**（来源：`ai_engine/core/schema.py:177-178`）

```python
_FIELD_PRIORITY  = ["topic", "duration_minutes", "style", "target_student"]
_REQUIRED_FIELDS = ["topic", "duration_minutes"]      # 仅这两项为必需
```

**追问策略**：按 `missing_fields` 生成问题，**单轮最多追问 2 个**（来源：`ai_engine/intent/intent_engine.py:79-91`，`questions[:2]`）。

**「最后一次明确表达优先」原则**：所有字段抽取都取**文本中最靠后的匹配**，以支持教师在确认前的自我纠错。

```python
# ai_engine/intent/rules.py:25
return max(matches, key=lambda item: item[0])[1]
```

**时长抽取区间**：只接受 **5 ≤ n ≤ 300 分钟**；支持「半小时」→30、「N 小时」→N×60（来源：`ai_engine/intent/rules.py:35-55`）。

**两条抽取链路**：

| 链路 | 实现 | 用途 |
|---|---|---|
| 规则兜底 | `IntentEngine.extract_intent()`（`intent_engine.py:44`） | 无 LLM 依赖，保证早期集成可跑通 |
| LLM 抽取 | `LLMIntentEngine`（`intent_engine.py:114`），模型 `qwen-turbo`，`temperature=0.1`，走 JSON Schema 约束 | 生产路径，另有 `extract_intent_stream()` 支持 SSE 流式 |

> 设计说明（来源：`ai_engine/intent/rules.py` 文件头注释）：规则同时服务 fallback 与 LLMClient mock，**避免两条链路行为漂移**。

### 3.2 多模态资料解析（C-02）— ✅ 已实现（部分依赖可选组件，含降级）

**分块策略映射**（来源：`ai_engine/rag/chunker.py:49-67`）

| 来源类型 | 切分策略 | chunk_size（token） | overlap |
|---|---|---|---|
| PDF | `paragraph`（按段落） | 512 | 64 |
| PPTX | `slide`（按幻灯片独立） | 0（不限制） | 0 |
| DOCX | `section`（按章节） | 0（每章节独立） | 0 |
| IMAGE | `sentence`（按句子） | 256 | 0 |
| VIDEO | `window`（固定窗口） | 256 | 32 |
| AUDIO | `window` | 256 | 32 |
| TEXT | `paragraph` | 512 | 64 |

> ⚠️ **文档与代码不一致，需修正**：`chunker.py` 文件头注释写「VIDEO 按时间窗口，**30s 段落 / 5s overlap**」「DOCX 按章节切分，**512 tokens / 64 overlap**」，而实际参数表为 VIDEO `256/32`、DOCX `0/0`。
> 注释描述的是设计文档 `KB-knowledge-base.md §5` 的原始设计，代码实现已改为上表值。**方案书应以代码为准**。

**chunk_id 决定论**（来源：`ai_engine/rag/chunker.py:156-163`）

- 格式：`{safe_source_ref}::s{seq_index:04d}`，**最长 64 字符**（适配 PG `VARCHAR(64)`）
- 长 `source_ref` 用 **md5 前 12 位**做前缀防碰撞
- 保证同一 `(source_ref, seq_index)` 永远得到同一 `chunk_id`，配合 store 层 `ON CONFLICT DO UPDATE` 实现**向量库幂等重建**

**各格式解析链路**

| 格式 | 实现文件 | 链路与产出 |
|---|---|---|
| PDF | `parse/doc_parser.py:150` `_parse_pdf` | 优先 marker（可选依赖），不可用时 `_read_as_plain_text` 兜底；产出按页的文本块 |
| PPTX | `parse/doc_parser.py:412` `_parse_pptx` | python-pptx 提取形状文本 + `_extract_ppt_images` 抽图 + `_describe_image`（`:345`）走 VLM 生成图片描述；`_build_pptx_result(elements, tool="unstructured")` 标注实际使用的工具 |
| DOCX | `parse/doc_parser.py:571` `_parse_docx` | 优先 unstructured，不可用时兜底；`_make_docx_chunk`（`:661`）产出 chunk |
| 图片 | `parse/ocr_engine.py:29` `OCREngine` | **PaddleOCR**（`lang="ch"`, `use_angle_cls=True`），产出含 `ocr_method: "paddleocr"` 的行文本 + `_analyze_layout`（`:210`）版面分析；PaddleOCR 缺失时抛错并提示安装命令 |

### 3.3 混合检索与证据融合（C-03 / C-04）— ✅ 已实现（重排为占位，⚠️ 部分规划中）

**融合公式**（来源：`ai_engine/rag/retrieve.py:4-7, 32, 158-183`）

```
score = 0.7 × vector_similarity(query, chunk) + 0.3 × bm25_score(query, chunk)
```

| 参数 | 值 | 来源 |
|---|---|---|
| 向量权重 `_VECTOR_WEIGHT` | **0.7** | `retrieve.py:32` 附近 |
| BM25 权重 `_BM25_WEIGHT` | **0.3** | `retrieve.py:32` |
| BM25 `k1` | **1.5** | `retrieve.py:51` |
| BM25 `b` | **0.75** | `retrieve.py:51` |
| 候选池大小 | `top_k × 4`，**封顶 200** | `retrieve.py:222` |

**BM25 实现**：纯 Python 零依赖，参考 Okapi BM25，**中文按单字切分 + 2-gram**（来源：`retrieve.py:39-51`）。

**嵌入模型**（来源：`ai_engine/rag/embed.py:34-47`）

| 参数 | 默认值 | 环境变量覆盖 |
|---|---|---|
| 模型 | `text-embedding-v3` | `AI_EMBEDDING_MODEL` |
| 维度 | **1024** | `AI_EMBEDDING_DIM` |
| 批大小 | **20**（上限 100） | — |

**降级路径（设计亮点，务必写进方案书）**：无 embedding key 时，向量全为零向量，混合分上限只剩 0.3（BM25 权重），会被 `min_score` 滤掉 → **自动退化为纯 BM25 检索**，保证 RAG 仍可用。
来源：`retrieve.py:212-234` 注释与 `_bm25_only_search` 分支。
