## 2. 本次迭代完成内容（已落地功能 / 修复问题）

**2.1 M1-1 — 修复 `questions` 字段类型冲突（schema.py）**

`TeachingNode.questions` 原定义为 `list[dict[str, Any]]`，但全链路所有 normalize 函数实际写入的都是字符串列表（每题为问题文本），前端 `_slide_quiz` 互动渲染也只期望字符串列表。类型声明与真实数据不匹配，属于隐藏的类型契约 BUG。修复：

```python
# 修复前
questions: list[dict[str, Any]] = Field(default_factory=list)

# 修复后
questions: list[str] = Field(default_factory=list)
```

统一为 `list[str]`，与 `interactive_questions` 等效，类型与所有写入方、消费方一致。

**2.2 M1-2 — 确认 16 字段双写对称性（schema.py）**

核对 `normalize_stage2_nodes` 与 `normalize_stage3_scripts` 两处规范化入口，确认以下 16 个字段全部双向对称写入、无遗漏：

`node_id / title / summary / source_span / node_type / type / prerequisites / key_points / core_points / questions / interactive_questions / segments / layout_hint / font_size_hint / text_alignment / slide_background`

其中两组兼容字段的 fallback 映射已存在且正确：

```python
"key_points": key_pts if key_pts else (core_pts if isinstance(core_pts, list) else []),
"questions": (item or {}).get("questions") or (item or {}).get("interactive_questions") or [],
```

结论：`key_points ↔ core_points`、`questions ↔ interactive_questions` 双向映射已落地，无需改动。

**2.3 M1-3 — 确认 `patch.py _handle_add` 字段完整性**

核对 `_handle_add` 新增节点 dict，确认基础标识、`node_type`/`type` 双写、4 组业务扩展字段、4 个排版元数字段、以及 `page_ref / source_chunk_ids / examples / key_difficulties / expected_outcomes / estimated_duration_minutes / interactive_questions / citation_refs / next_node_id / prev_node_id / metadata / source_span / prerequisites` 等全部字段齐备，无缺失，无需改动。

**2.4 连带修复 — 两个阻塞全体成员的 P0 级启动故障（main.py）**

排查生成链路 500 时发现两处全局阻断项（非本模块独有，但直接影响我负责的数据层可用性）：

- **`SyntaxError: 'await' outside async function`**：`_run_generation_pipeline` 被改为同步 daemon 线程执行后，残留 8 处 `await _persist_generation_task(task)` 未改。新增同步持久化函数 `_persist_task_sync()`（内部走 `asyncio.run()` 或线程安全的 `_mem.save_task`），并替换全部 8 处调用。
- **`asyncio.Lock` 跨线程误用**：`_gen_tasks` 字典同时被事件循环线程（async 端点）与 daemon 生成线程访问，原 `asyncio.Lock()` 既非线程安全、也无法在同步线程里用 `with` 使用，导致 gen/create 500。改为 `threading.Lock()`，并将对应的 `async with` 改为 `with`。

修复后验证：`gen/create → gen/status` 全链路返回 `done`，生成 3 个节点，磁盘快照 `data/versions/{gen_id}/v_1.json` 中 `questions` 已为正确字符串列表。

## 3. 当前模块现存可发现问题 & 未完全解决的遗留隐患

**3.1 `core_points ↔ key_points` 仅读取时 fallback，写路径未双向同步**

normalize 层只在"读取时"用 `key_pts if key_pts else core_points` 兜底；但 `_handle_add` 中 `key_points` 固定写空列表 `[]`、`core_points` 从参数继承，`UPDATE_NODE` 更新 `core_points` 时也不会同步 `key_points`。两者在"写路径"上可能长期不一致，消费方读哪个字段存在歧义。

**3.2 `type` 字段写路径未做小写规范化**

`_handle_add` 中 `"type": raw_type` 直接写原始值。若命令传入 `"Section"` 等非标准大小写，`type`（原始值）与 `node_type`（规范化为 `"SECTION"`）会不一致，渲染层类型识别存在大小写不匹配隐患。

**3.3 旧版本磁盘快照未做 schema 迁移验证**

`questions` 类型从 `list[dict]` 改为 `list[str]` 后，历史快照（`data/versions/*/v_N.json`）的反序列化仅依赖 Pydantic 默认值补齐，未经真实旧快照加载测试，无法确认所有边界情况（字段为 null、类型不匹配）下均无异常。

**3.4 Redis 重启持久化的嵌套对象反序列化不完整（关联 P2-4）**

`_persist_task_sync` 依赖的 `RedisTaskStore._deserialize` 仅按字符串前缀 `[`/`{`/`"` 判断是否 JSON 反序列化，`nodes`、`intent`、`evidence` 等嵌套 list/dict 字段在 Redis 往返后可能仍是字符串而非结构化对象，重启后 `load_task` 拿到的节点数组可能不可用。且 Redis 缺席时任务状态只存进程内存，进程重启即全部丢失。

**3.5 mock 模式覆盖不充分**

当前 AI Engine 运行在 mock 模式（无真实 LLM 凭证），`questions`/`key_points` 的真实 LLM 写入路径（`generate_enhanced` 等）未经真实数据验证，规范化逻辑在真实输出下的健壮性待确认。

## 5. 后续可优化方案 & 迭代建议

**5.1 建立 `core_points ↔ key_points` 写路径统一封装**

在 `patch.py` 各 handle 方法及 `node.py` 生成入口，将"双字段同步写"收敛到一个工具函数（或 TeachingNode 模型层的 `@model_validator`），从源头保证两字段恒等，而非只靠读取时 fallback。

**5.2 `type` 字段写入口统一 `.lower()` 规范化**

在 `_handle_add` 及 `outline.py`/`node.py` 所有节点生成入口统一 `raw_type.lower()`，保证 `type` 全链路小写、与 `node_type` 映射一致。

**5.3 补充旧快照迁移脚本**

对 `data/versions/` 历史快照做一次性扫描，对缺失字段或 `questions` 仍为 dict 结构的节点原地补齐，支持 `--dry-run` 预览，避免运行时边界异常。

**5.4 完善 Redis 反序列化类型恢复**

`_deserialize` 不能仅靠字符串前缀猜测，应基于字段级类型元数据（或对 `nodes`/`intent`/`evidence` 等已知结构化字段显式 `json.loads` + Pydantic 校验）恢复对象，保证重启后任务可真正恢复。

**5.5 接入真实 LLM 后补集成测试**

配置真实凭证后，补充针对 `questions`/`key_points` 真实写入路径的集成测试，验证规范化在 LLM 非标准输出下的健壮性。

## 6. 本次开发总结

**开发难点：**

本次最耗时的环节是厘清"类型声明"与"真实数据"之间的契约错位 —— `questions` 字段声明为 `list[dict]`，但全链路实际写的都是 `list[str]`，这属于一种"代码表面正确、运行时靠各写入方自觉保持"的隐性隐患，需要逐个核对 normalize、patch、前端消费方才能确认正确类型。其次是排查 gen/create 500 时定位到的两处线程/事件循环混用问题（`asyncio.Lock` 跨线程 + sync 函数内残留 `await`），这类问题只在"异步端点 + 同步 daemon 线程"双上下文并存的架构下才会暴露。

**主要收获：**

建立了从数据结构定义（core/schema.py）→ 规范化（schema.py）→ 节点生成/修补（gen/patch.py）→ 内存存储（main.py `_gen_tasks`）→ 磁盘/Redis 持久化的完整数据流图谱，并明确了"读取时 fallback 兜底"与"写路径源头统一"是两种不同层次的治理手段，前者救急、后者治本。

**卡点与解决：**

主要卡点是生成链路 500 由线程模型改造（daemon 线程化）引入、且横跨本人与成员 4 的职责边界。最终选择就地修复而非回滚 —— 新增 `_persist_task_sync` 兼容同步上下文、将锁替换为 `threading.Lock`，在保持 daemon 线程异步架构的前提下恢复可用性。

**与其他模块的适配对接：**

本次严格不触碰接口契约，对外 JSON 格式不变，前端 / Go Backend 无感。连带修复的两处 P0 故障是共享基础设施，使成员 2/3/4 得以继续联调，属于对整体交付的直接解锁。

**遗留风险提示：**

最大遗留风险是 `core_points`/`key_points` 写路径不同步（5.1）与 Redis 重启持久化反序列化不完整（5.4），建议在接入真实 LLM 与正式上线前优先补齐，确保真实课件数据与多版本迭代场景下行为符合预期。
