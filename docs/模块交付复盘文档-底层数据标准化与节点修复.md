## 2. 本次迭代完成内容（已落地功能 / 修复问题）

**2.1 TeachingNode 数据结构升级（schema.py）**

在 TeachingNode 模型中原有 17 个字段基础上，新增 8 个标准化字段，全部赋予空值或空列表默认值，保障新旧数据完全兼容：

- 新增 `type: str = ""` — 渲染层 type 字符串，与 node_type 枚举等效，解决渲染层只能读 type 的兼容问题
- 新增 `key_points: list[str] = Field(default_factory=list)` — 要点列表，对齐主流 AI-PPT 开源规范，与 core_points 并存
- 新增 `segments: list[dict[str, Any]] = Field(default_factory=list)` — 内容分段结构，含 title、content、duration_minutes
- 新增 `questions: list[dict[str, Any]] = Field(default_factory=list)` — 内嵌问答结构，含 question、answer、type
- 新增 `layout_hint: Optional[str] = None` — 布局类型提示（title_only / text_with_media / quiz 等）
- 新增 `font_size_hint: Optional[str] = None` — 字号提示（large / medium / small）
- 新增 `text_alignment: Optional[str] = None` — 文本对齐方式（left / center / right / justify）
- 新增 `slide_background: Optional[str] = None` — 幻灯片背景 CSS 值

**2.2 patch.py 新增节点逻辑重构（_handle_add）**

原有 `_handle_add` 仅写入 7 个字段，缺失大量 TeachingNode 必填字段，导致新增节点在预览/导出时字段缺失、渲染异常。重构后新增节点自动包含：

- `node_type`（枚举字符串形式：SLIDE / SECTION / QUIZ 等）与 `type`（渲染字符串：slide / section / quiz 等）双写且互相同步
- `key_points: []`（空列表，默认值）
- `core_points` 从命令参数继承
- `segments: []`、`questions: []`（空列表）
- 全部 4 个排版元数字段（layout_hint / font_size_hint / text_alignment / slide_background 均为 None）
- 补齐 page_ref、source_chunk_ids、examples、key_difficulties、expected_outcomes、estimated_duration_minutes、interactive_questions、citation_refs、next_node_id、prev_node_id、metadata 等 TeachingNode 全部原有字段

**2.3 字段映射规则统一（preview.py + export_ppt.py）**

针对 node_type / type 和 core_points / key_points 两组字段在预览/导出层的识别冲突问题，完成以下规范化修复：

**preview.py（预览渲染层）：**

- `_render_slide` 方法：类型识别从 `node.get("type") or "content"` 改为 `type or node_type or "content"`，优先读取 type，node_type 为备选，彻底解决纯旧数据（仅有 node_type 枚举值）无法正确渲染的问题

**export_ppt.py（PPTX 导出层）：**

- `export` 方法：类型识别改为 `type or node_type or "content"`，与预览层一致
- `export_to_bytes` 方法：同上，统一两处导出入口的类型判断
- `_add_content_slide` 方法：内容读取顺序从 `content/script/summary/core_points` 扩展为 `content/script/summary/core_points/key_points`，确保新增的 key_points 要点数据在 PPTX 内容页中被正确导出
- `_add_summary_slide` 方法：总结页要点读取从 `key_points or summary` 扩展为 `key_points or core_points or summary`，解决总结页在仅有 core_points 无 key_points 时数据丢失的问题

**2.4 内存与磁盘数据同步修复（main.py）**

原 `modify_nodes` 接口在保存新版本快照（save_snapshot）后，未同步刷新进程内 `_gen_tasks` 字典中的任务数据，导致前端轮询 `/api/v1/gen/status/{task_id}` 时拿到的是 Patch 前的旧节点数组，这是数据状态不一致的核心阻断 BUG。修复方案：

- 在 `save_snapshot` 成功后，立即调用 `load_version` 读取最新磁盘快照
- 将最新节点数组同步写回 `_gen_tasks` 中对应 `generation_id` 的任务对象
- 同时将任务状态修正为 DONE、stage 修正为 DONE、progress_pct 修正为 100.0
- 前端下次轮询即可拿到 Patch 后的正确数据

## 3. 当前模块现存可发现问题 & 未完全解决的遗留隐患

**3.1 patch.py _handle_add 的 type 字段写入值存在大小写不一致风险**

在 `_handle_add` 中，`type` 字段写入的是原始传入值（如 "slide"、"SECTION"），而 `node_type` 写入的是规范化后的枚举字符串（如 "SLIDE"）。如果命令参数中传入 `"Type": "Section"`（非标准小写），type 字段将直接写入未规范化的原始值，与 node_type 不一致，可能导致渲染层类型识别时大小写不匹配。

当前 `type` 字段在 `_handle_add` 中的赋值语句为 `"type": raw_type`，而 `raw_type` 仅来自 `cmd.params.get("node_type") or cmd.params.get("type", "slide")`，未做小写规范化处理。预览层和导出层虽然已加 `.lower()`，但 type 字段本身值不规范仍是隐患。

**3.2 _gen_tasks 内存同步在后台生成任务运行期间可能产生竞态条件**

`modify_nodes` 中的内存同步逻辑在遍历 `_gen_tasks` 时没有加锁保护，而 `_gen_tasks` 的写操作由 `asyncio.Lock()` 保护。在 `_run_generation_pipeline` 后台任务正在执行期间（特别是正在执行 save_snapshot 写盘操作时），外部调用 `modify_nodes` 可能触发内存与磁盘的并发写入，存在极短时间窗口内的数据覆盖风险。

当前同步逻辑未使用 `_gen_tasks_lock`（async Lock），但读取 `_gen_tasks` 本身是读取操作，风险较低。真正的风险在于：后台生成任务和修改命令同时作用于同一个 generation_id 时的状态合并逻辑未经测试验证。

**3.3 内存同步未覆盖 _export_tasks 的 nodes 字段**

`modify_nodes` 的内存同步逻辑仅更新了 `_gen_tasks` 中的 `nodes` 字段，但导出任务 `_export_tasks` 内部不存储 nodes 数组（nodes 通过 `load_version` 实时读取磁盘），因此不存在此问题。但若未来有其他模块直接持有节点数据引用而非通过 `load_version` 读取，则可能遗漏同步。

**3.4 旧数据（无新增字段）的 schema 兼容性问题未完整验证**

TeachingNode 新增字段均设置了默认值，但旧版本磁盘快照文件（`data/versions/{gen_id}/v_N.json`）中已保存的 TeachingNode 节点对象在反序列化时，Pydantic 会自动用默认值补齐缺失字段。当前代码层面理论上兼容，但未经实际旧版本快照加载测试，无法确认反序列化流程是否在所有边界情况下（如字段为 null、字段类型不匹配）均无异常。

**3.5 core_points 与 key_points 双向同步未实现**

当前 `patch.py` 的 `_handle_add` 中，`key_points` 固定为空列表 `[]`，而 `core_points` 从命令参数继承。但若用户通过 `UPDATE_NODE` 命令更新了节点的 `core_points`，对应节点的 `key_points` 不会自动同步更新，反之亦然。这导致两个字段在同一条节点数据中可能长期不一致，前端预览/导出时读哪个字段就有歧义。

## 5. 后续可优化方案 & 迭代建议

**5.1 type 字段写入规范化**

在 `patch.py` 的 `_handle_add` 中，对 `type` 字段写入前统一做小写规范化处理：

```python
"type": raw_type.lower(),  # 确保 type 始终为小写字符串
```

同时在 `outline.py` 和 `node.py` 等节点生成入口处，也应统一对 `type` 字段做 `.lower()` 规范化，确保从大纲构建到节点生成全链路 type 字段格式一致。

**5.2 修改命令执行路径加锁保护**

在 `main.py` 的 `modify_nodes` 函数中，将内存同步逻辑包裹在 `async with _gen_tasks_lock:` 临界区中，与后台生成任务共享同一把锁，消除并发写入风险：

```python
async with _gen_tasks_lock:
    for tid, task in _gen_tasks.items():
        if task.generation_id == req.generation_id:
            task.nodes = refreshed_nodes
            task.status = GenerationStatus.DONE
```

**5.3 旧版本快照 schema 迁移工具**

编写独立脚本对 `data/versions/` 目录下所有历史快照文件进行扫描，对缺少新增字段的 TeachingNode 节点对象进行原地补全，自动填充默认值字段（key_points、segments、questions、layout_hint 等），避免运行时因字段缺失导致的边界问题。迁移脚本应支持 dry-run 模式以供验证。

**5.4 core_points 与 key_points 双向同步机制**

在所有节点写入路径（`patch.py`、`node.py`、`main.py` 中的 `_run_generation_pipeline`）统一增加同步逻辑：当 `core_points` 被更新时，自动将 `key_points` 同步为相同值（反之亦然）。推荐在 TeachingNode 的 Pydantic 模型层或工具函数层统一封装写入方法，而非在各调用方分散处理。

**5.5 集成测试覆盖**

建议补充针对以下场景的集成测试用例：

- 新增节点后磁盘快照中所有字段完整写入并可正确加载
- 仅有 node_type（无 type）的旧节点在预览和导出时能正确识别渲染类型
- 仅有 core_points（无 key_points）的节点在导出总结页时能正确读取要点
- `modify_nodes` 后前台轮询能拿到 Patch 后的最新节点数组
- 并发执行生成任务与修改命令时数据无覆盖丢失

## 6. 本次开发总结

**开发难点：**

本次开发的核心难点在于**字段双轨制**带来的识别冲突问题。项目中 `node_type`（枚举）和 `type`（字符串）同时存在于 TeachingNode 中，而不同消费方（预览渲染、PPTX 导出、大纲构建、节点生成）分别只读取其中一个字段，导致同样一条节点数据在某些消费方下可正常展示，在另一些消费方下则类型识别降级为默认类型（content），且旧数据（仅有 node_type 枚举值）完全无法被仅读 type 的消费者识别。厘清全链路字段流转路径并逐个修复消费方，是本次最花时间的环节。

**主要收获：**

通过本次开发，建立了从数据结构定义（schema.py）→ 节点生成（patch.py）→ 内存存储（main.py _gen_tasks）→ 磁盘持久化（version.py save_snapshot）→ 预览/导出消费（preview.py / export_ppt.py）的完整数据流图谱，清晰定位了每个环节的字段生产和消费关系，为后续维护和扩展奠定了基础。

**卡点与解决：**

主要卡点是 patch.py 的 `_handle_add` 原本字段严重不全（仅 7 个字段），而项目中没有任何统一的位置对新增节点做完整的字段初始化，最终选择在 patch.py 的 `_handle_add` 中一次性补齐所有字段，而非分散在多个消费方做默认值适配，符合"数据在源头完整"的原则。

**与其他模块的适配对接：**

本次修改严格遵守了不对接口契约开刀的原则，对外暴露的数据格式（JSON 序列化后的 TeachingNode 节点数组）保持不变，因此无需与前端、Go Backend 做适配对接。新增字段以默认值形式存在于 schema 定义中，调用方无感知。但内存同步逻辑（刷新 _gen_tasks）属于进程内私有实现，若未来将 AI Engine 部署为独立微服务，该部分逻辑需随进程共享存储方案（Redis）一并迁移。

**遗留风险提示：**

当前最大遗留风险是 `core_points` 与 `key_points` 双向同步未实现，以及旧版本快照的 schema 迁移未经实际验证，建议在正式上线前完成这两项补充工作，以确保在真实课件数据（尤其是经过多次版本迭代的课件）场景下系统行为符合预期。
