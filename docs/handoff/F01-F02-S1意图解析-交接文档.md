## 二、项目背景

### 2.1 项目是什么

把原有的"泛雅 AI 智课系统"（讲授型课件 + 学生 Q&A）重构为 **"多模态 AI 互动式教学智能体"**：
教师多轮对话 → 多模态资料融合 → 智能课件生成 → 预览修改 → 版本导出。

### 2.2 技术架构

```
教师端前端 (Vue 3 + Vite, :5173)
        │  HTTP
        ▼
Go 后端网关 (Gin, :8082)  ──AI Engine 调用／SSE 流式／鉴权
        │  HTTP
        ▼
Python AI Engine (FastAPI, :8000)  ──LLM 调用／解析／生成／RAG
        ▼
真实大模型 (OpenAI 兼容端点，配置项 ai.base_url)
```

数据层：PostgreSQL + Redis + MinIO。

### 2.3 S1 在整条链路里的位置

S1 是**整条链路的第一个环节**，也是唯一直接和"教师自然语言"打交道的环节。
后续 S2（资料解析）、S3（课件生成）、S4（个性化）全部消费 S1 输出的结构化意图。

所以 S1 出错的代价被放大：**S1 把知识点抽错，S3 就会把错的知识点写进课件正文**，且用户看不出错在哪。

### 2.4 S1 的接口契约

请求 `POST /api/v1/intent/extract`：

```json
{
  "session_id": "任意字符串",
  "messages": [{ "role": "teacher", "content": "教师的自然语言原话" }]
}
```

响应关键字段（**本次改动涉及加粗项**）：

| 字段 | 含义 | 取值 |
|---|---|---|
| `intent_summary` | 结构化教学意图 | `topic` / `duration_minutes` / `style` / `target_student` / `knowledge_points` / `output_format` / `with_interactive` / `key_difficulties` / `expected_outcomes` / `missing_fields` |
| `engine` | 实际产出结果的引擎类名 | `LLMIntentEngine` / `IntentEngine` |
| `used_fallback` | 是否降级到规则引擎 | bool |
| `degraded` | `used_fallback` 的显式别名 | bool（**本次修正为始终存在**） |
| `fallback_reason` | 降级根因 | `timeout` / `engine_unavailable` / `model_error` / `invalid_model_response` / `mock_mode` / `missing_api_key_mock` |
| **`model_source`** | **本次结果到底是谁算出来的** | `real_model` / `mock` / `rule_fallback` / `rule_engine` |
| **`normalization_notes`** | **模型输出被怎样修正过** | 字符串数组，非空 ⇔ 模型输出被采用 |
| `completion_pct` | 方案完整度（0–100） | int |
| `session_status` | 会话阶段 | `collecting` / `clarifying` / `confirming` |

## 五、改动详解：根因 → 修复 → 证据

### A. F01 —— 真实模型输出格式校验

#### 现象

模型只要有**任意一个字段**类型不对（哪怕那个字段跟主题毫无关系），
**整包模型结果被丢弃**，全量回退规则引擎。

#### 根因

`ai_engine/intent/service.py` 里的 `IntentSummary(**result)` 是**整包 pydantic 校验**。

模型返回 `with_interactive: "需要"`（中文，而不是 `true`）→ 抛 `ValidationError` →
`topic` / `duration_minutes` / `style` / `knowledge_points` **全部被一起扔掉**。

更糟的是降级原因被记成 `model_error`（像"服务挂了"），**掩盖了真正的问题**（只是格式没对齐）。

#### 修复

新增 `ai_engine/intent/normalize.py`（252 行），把模型原始输出**逐字段归一后再校验**：

| 模型返回 | 归一后 | 备注 |
|---|---|---|
| `"45分钟"` | `45` | 时长 |
| `"需要"` | `True` | 布尔 |
| `"PPT"` | `"ppt"` | 输出格式 |
| `["冒泡排序, 快速排序"]` | `["冒泡排序","快速排序"]` | 逗号串拆列表 |
| `["flash"]` | `[]` | 非法项**单独丢弃**，不牵连其它字段 |
| 多余字段 `reasoning` | 丢弃 | 不报错 |

关键点：

- **能归一的字段就地归一**；
- **无法归一的字段单独丢弃并留下说明**，不牵连其它字段；
- 只有当**关键字段（主题）**仍不可用时，才由调用方判定整包失败并回退规则引擎。

归一说明随响应返回（`normalization_notes`），契约是：

> **`normalization_notes` 非空 ⇔ 模型输出被采用**。
> （降级时模型输出未被采用，因此不带说明 —— 这条契约让"模型输出被采用"可被外部判定。）

Go 网关 `IntentExtractResponse` 增加 `NormalizationNotes` 字段透传 ——
**否则该字段会在网关结构体序列化时被静默丢弃，可观测性形同虚设。**

#### 证据

固定样例（团队统一测试样例）修复前后对照，同一个受控模型端点：

| | 修复前 | 修复后 |
|---|---|---|
| `engine` | `IntentEngine` | `LLMIntentEngine` |
| `used_fallback` | `True`（模型结果被整包丢弃） | `False` |
| `knowledge_points` | `['互动选择题']` | `['冒泡排序', '快速排序']` |
| `normalization_notes` | `None` | `["with_interactive: '需要' → True"]` |
| 界面完整度 | 85% | 100% |

### B. F02 —— 规则覆盖知识点

#### 现象

教师已经说过的知识点被清空，`missing_fields` 仍标记缺知识点，
系统反过来追问教师**已经给过的**信息。

#### 根因

`service.py` 的 `_merge_rule_evidence` 里有一行**直接赋值**：

```python
summary.knowledge_points = rule_summary.knowledge_points   # ← 直接覆盖
```

教师说"帮我做快速排序课件"（没写"知识点/包括"等触发词）时规则抽不到知识点 →
**模型正确抽出的知识点被清空**。

#### 修复（合并策略，不是覆盖）

| 教师是否**明确标注**知识点 | 行为 |
|---|---|
| 是（"知识点：…"、"核心知识点：…"、"重点包括/讲解…"） | **以规则为准**（清单最可信） |
| 否 | **保留模型结果**，但必须通过接地校验 `is_grounded_knowledge_point()` |

接地校验要求知识点能在**教师原话**中找到依据：

- 双向包含（教师说"分治"、模型说"分治思想"）要求教师原话足够具体才成立，
  避免一句短话把无关知识点全部"接地"；
- 碎片过滤 `filter_knowledge_point_fragments()` 排除风格、对象、互动等**跨字段碎片**。

#### 真实链路验收时新发现的两个同源缺陷

> ⚠️ **这两个是"跑真实链路"才暴露的 —— 单元测试用的是显式标注的知识点，触发不到。**
> 这也是为什么单测全绿 ≠ 功能正确。

| 缺陷 | 现象 | 根因 |
|---|---|---|
| **知识点被"包含"污染** | 固定样例里"教师要求**包含**互动选择题"→ 规则把"互动选择题"当成知识点；且规则命中即**整体替换**模型结果，模型正确抽出的核心知识点被顶掉 | 规则的知识点触发词含"包含/包括/涉及/涵盖"等**普通动词** |
| **输出格式被"课件"覆盖** | 模型已归一好的 `["ppt","doc"]` 被压成 `["ppt"]` —— 等于让 F01 的归一成果在合并阶段被丢弃 | 合并阶段覆盖条件含"课件"，而它几乎出现在每一句教学需求里（"做一节XX课件"） |

**修复**：

- 拆分触发词强度 ——
  - 新增 `extract_explicit_knowledge_points()`：**只认**"知识点：""核心知识点：""重点包括/讲解"这类显式标注（高置信度）；
  - `extract_knowledge_points()` 的松散动词分支改为**先过滤要求类片段**（互动/格式/时长/风格），一条不剩即视为**规则未命中**，交回模型分支；
- 输出格式只在教师**明确点名**格式（PPT/幻灯片/Word/教案/讲义/讲稿）时才用规则结论覆盖；
  模型没给格式**且**教师也没点名时才用默认值。

#### 附带修复：主题置信度

新增 `extract_topic_strict(text) -> str | None`：只有高置信度主题才能覆盖模型主题。

避免规则生成"做45分钟快速排序"这类**脏值**（把修饰语拼进主题）。

### C. V04：结果来源可观测性（本次会话新增）

> 这一块**不在原分工里**，是真实链路验收时主动发现并补上的。
> 它直接对应执行方案第七条第 5 点与待核验事项 V04。

#### 现象（真实复现）

服务器部署配置 `deploy/docker-compose.server.yml` 里 **`AI_GEN_MODE` 默认是 `mock`**。
此时候选接口返回：

```
used_fallback   = false
degraded        = false
fallback_reason = null
```

**界面完全看不出"这次结果到底是谁算出来的"** —— 把 HTTP 200 等同于真实模型成功，
直接违反执行方案第七条第 5 点「真实模型成功、规则兜底成功、离线测试通过、模拟链路通过不能混为一谈」。

更隐蔽的是**根因被掩盖**：缺 API Key 时，`llm.py` 会静默回退到内置 mock 桩，
但降级原因被记成 `invalid_model_response`（"模型输出无效"）——
把"压根没调模型"误报成"模型坏了"。

#### 修复

**Python 侧**

- `LLMClient.unavailable_reason()`：判定本次调用能否触达真实模型，区分
  - `mock_mode` —— 显式 mock 模式；
  - `missing_api_key_mock` —— 未配置 API Key，回退到内置桩；
  - 空串 —— 可以调真实模型。
- `LLMIntentEngine` 在**调用过程中**记录 `last_unavailable_reason`
  （注意：必须在 `extract_intent()` **之后**读，因为状态是调用时写下的）。
- `IntentUnderstandingService` 新增 `model_source` 字段，取值：

  | 值 | 含义 |
  |---|---|
  | `real_model` | 真实模型输出被采用（含轻度归一） |
  | `mock` | **没有调用真实模型**（mock 模式 / 未配置 API Key） |
  | `rule_fallback` | 模型侧失败，已回退规则引擎 |
  | `rule_engine` | 规则引擎直接产出（显式规则模式） |

- 修正降级根因：缺 Key 时不再记成 `invalid_model_response`，如实记录 `missing_api_key_mock`。

**Go 网关侧**

- `IntentExtractResponse` 增加 `ModelSource` 透传字段。
- **修正 `Degraded` 字段的 `omitempty`** —— Python 侧无条件输出该字段，
  网关不该在值为 `false` 时把整个键省略，否则下游读到 `undefined` 而非 `false`。
  （这是我在真实链路里抓原始 JSON 键才发现的契约不一致。）

**前端侧**

- `intentStore` 接收并持久化 `model_source`。
- `TeacherIntentPanel` 按来源给出**三种不同**提示：

  | 来源 | 界面提示 |
  |---|---|
  | `real_model` | **不提示** |
  | `rule_fallback` | 「当前使用本地规则提取（AI 服务返回异常）」—— 带具体原因 |
  | `mock` / `rule_engine` | 「当前未接入真实模型（本地模拟/规则模式），识别结果仅供参考」 |
  | 空串（来源未知/旧数据） | 按旧逻辑只依据 `used_fallback`，不臆断 |

## 八、踩坑清单（重要）

> 这些都是本次真实花时间才定位到的，写下来是为了下一个人不用再走一遍。

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | **前端会静默切 mockBackend** | Go 后端不可达时，前端不报错，改为返回内置 mock 数据 —— 界面看着正常，全是假的 | 浏览器测试必须**抓真实响应体**，校验 `engine`/`used_fallback`/`model_source` 等 mock 没有的字段 |
| 2 | **"接口 200"不等于"模型跑通"** | 模型结果被整包丢弃后照样回退规则引擎并返回 200 | 查 `used_fallback` + `model_source`，不能只看 HTTP 状态码 |
| 3 | **缺 Key 时根因被掩盖** | 降级原因记成 `invalid_model_response`，像是"模型坏了" | 本次已修：如实记 `missing_api_key_mock` |
| 4 | **Go 网关会静默丢字段** | Python 有的字段，网关结构体没声明就**整个消失** | 每次加 Python 响应字段，必须同步查 Go 结构体 |
| 5 | **`omitempty` 会吃掉 `false`** | `Degraded bool` 带 `omitempty`，值为 false 时整个键消失，下游读到 `undefined` | 布尔字段与 Python 侧输出策略对齐；本次已修 |
| 6 | **JS 模板字符串 ≠ Vue 模板** | 在 computed 里写 `` `{{ x.value }}` `` 会**原样显示** `{{ x.value }}` | JS 里用 `${x.value}`；Vue 模板里才用 `{{ x }}` |
| 7 | **`page.addInitScript` 里没有 `process.env`** | 浏览器上下文执行，读 `process.env` 直接抛 ReferenceError | 用 `page.addInitScript((arg) => {...}, value)` 传参 |
| 8 | **Python 脚本改文件会改写行尾** | 用 `io.open(p,"w")` 重写 JS 文件，LF 变 CRLF → diff 显示几百行，实际只改了几行 | 写文件前用 `newline=''`，或写完检查 `\r\n` 数量；改完用 `git diff -w` 复核真实改动量 |
| 9 | **worktree 缺未跟踪文件** | 干净基线上某个测试反而"通过"，主仓库失败 —— 因为差异来自未跟踪资源 | 对照测试要用 `git worktree` + 复现未跟踪资源，不能只看一边 |
| 10 | **Go 不在 PATH** | `go: command not found` | `export PATH="/d/Program Files/Go/bin:$PATH"`，另设 `GOCACHE`/`GOPATH` |
| 11 | **origin 内嵌 Token 会失效** | push 报 401 | 用 Git Credential Manager：`git credential fill` 取凭据，**并把 URL 里的 Token 移除** |
| 12 | **`git stash pop` 易冲突** | 还原工作区时冲突 | 优先用 `git worktree` 做基线对照；必须 stash 时先 `git stash list` 确认不会误 pop 别人的 stash |
| 13 | **复制文件会带进无关改动** | 从 `server-deploy` 复制 Go 文件，误带 S3 SSE 代码 | 还原到基线后**只重新加入需要的几行**，不整文件覆盖 |
| 14 | **`AI_ENGINE_BASE_URL` 没有 `APP_` 前缀** | 设了 `APP_AI_ENGINE_BASE_URL` 没生效 | 显式 `BindEnv` 的变量名不带前缀 |

## 九、关键设计决策与被否决的方案

### 9.1 决策：知识点合并而非覆盖

**否决的方案**：保持"规则命中就整体覆盖模型结果"。
**否决理由**：规则触发词是模糊的（"包含/包括"），一旦命中就整体替换，
会把模型正确抽出的核心知识点顶掉 —— 这正是 F02 原始缺陷的成因。

**采纳**：教师明确标注 → 规则优先；否则保留模型结果但要通过接地校验。

### 9.2 决策：不从课程主题反推知识点

规则未命中知识点时，**不**用课程主题去猜。

**理由**：主题是课程名（如"冒泡排序与快速排序"），从它反推知识点属于**凭空推断**，
会让系统不再追问真正缺失的信息。

> ⚠️ **这一点我先做错过一次。** 曾加过"从主题推导知识点"的兜底，
> 结果打破了团队既有断言
> `test_extracts_natural_teacher_request_without_polluting_knowledge_points`
> （该断言要求自然请求的知识点必须为空），已撤回。
> **记在这里，避免后续有人再踩。**

### 9.3 决策：降级时 `normalization_notes` 置空

降级到规则引擎时模型输出**未被采用**，因此不带归一说明。
这样 `normalization_notes` 非空 ⇔ 模型输出被采用，契约对外部可判定。

### 9.4 决策：`model_source` 用四值而非布尔

一开始想用 `is_real_model: bool`，但那样表达不了
"模型试过了但失败了"（`rule_fallback`）和"规则引擎直接产出"（`rule_engine`）的差别。
四值语义更准，也和 V04 要求核验的三态对齐。
