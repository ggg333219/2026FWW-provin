# 新会话初始提示词 —— A12 多模态 AI 互动式教学智能体

> **这份文件解决一个具体问题**：AI 会话的开场状态如果不加约束，
> 助手会基于"看起来合理"的假设直接动手 —— 拉错分支、覆盖队友改动、
> 拿单测全绿当验收通过、在 mock 链路上宣称功能正常。
>
> 所以下面这份提示词**不描述任务，而是先固定"允许做什么、不允许做什么、
> 什么算证据"**。任务本身由团队另行给出。

## 一、怎么用这份提示词

### 1.1 使用时机

**在打开任何代码之前**，把提示词作为新会话的第一条消息发给 AI。
之后的第一轮回复里，AI 应该完成"环境接管"（见第二节第 0 段），而不是直接改代码。

### 1.2 三条使用原则

| 原则 | 说明 |
|---|---|
| **先看现状，再动手** | 提示词要求 AI 先做只读检查并**回报发现**，再动手。目的是让 AI 在"信息不足"时暴露假设，而不是掩盖 |
| **约束要能被检查** | 每条约束都配了**可执行的判定方式**（命令、断言、文件），而不是"请认真""请仔细"这类无法验证的话 |
| **证据分级要写死** | 明确"什么算通过、什么不算"，杜绝"单测全绿 = 功能正常" |

### 1.3 配套的"良好开始环境"

一份好的初始提示词要配合一个**可复现的起始环境**才有效。本项目的起始环境清单：

| 要素 | 位置 / 准备方式 |
|---|---|
| 项目全貌 | 仓库根目录 `AGENTS.md`（拖给 AI 就能理解整个项目） |
| 本次任务的完整上下文 | `docs/handoff/F01-F02-S1意图解析-交接文档.md`（自包含，含踩坑清单） |
| 基线锚点 | `submission-package-1009` @ `e431d0c`（对照用的干净起点） |
| 可运行的环境 | 见交接文档第 7 节「环境搭建手册」（五件套全部有可复制命令） |
| 验证脚本 | `tmp/` 下（已 gitignore，克隆后按交接文档第 12 节重建） |
| 证据标准 | 见本文件第二节「证据分级」 |

> **原则**：交接文档必须**自包含**。
> 新会话不应该需要"问上一个会话的人"才能继续 —— 凡是能写下来的都要写下来，
> 尤其是**踩过的坑**和**被否决的方案**。

## 二、通用模板（换项目复用）

> 把 `<尖括号>` 里的内容替换掉即可。方括号 `[...]` 内的说明是给写模板的人看的，**不要保留**。

```
你将接手 <项目名> 的 <模块名> 部分工作。

## 0. 先接管环境，不要立即动手

在修改任何文件之前，请先完成下列**只读**检查，并把发现**回报给我**：

1. 执行 `git fetch --all && git status && git branch -vv && git log --oneline -10`，
   报告：当前分支、是否有未提交改动、当前 HEAD 与远程是否同步。
2. 阅读 <交接文档路径>，确认你已理解任务边界、已成的工作、验证方式与遗留问题。
3. 报告你对本次任务范围的**理解**，以及你**打算先验证什么**。
   如果我给的信息有缺漏或自相矛盾，**明确指出**，不要自行猜测填补。

在我确认之前，只做只读检查。

## 1. 任务范围

- 基线：<基线分支> @ <基线 SHA>
- 工作分支：<分支名>（如已存在则在其上继续；否则从基线新建）
- 本次负责：<任务清单>
- 明确**不在**范围内：<不负责的部分> —— 遇到时**报告**，不要顺手改

## 2. 硬性约束

1. **只提 PR，不直接合并。** 合并由负责人决定。
2. **不改动范围外的代码。** 看到别处的问题就报告，不要顺手修。
3. **不提交队友的未跟踪产物。** 只提交你自己创建的、属于本次任务的文件。
4. **不写入任何密钥、token、个人信息。** 提交前自查。
5. **不删除他人文件。** 需要清理时先列清单并征得同意。

## 3. 证据分级（最重要的一条）

**从低到高，只有达到对应级别才能宣称"通过"：**

| 级别 | 证据 | 能证明什么 |
|---|---|---|
| L0 | 代码写完了 | 什么都证明不了 |
| L1 | 单元测试通过 | 该函数的**纯逻辑**正确 |
| L2 | 集成/接口层测试通过 | 多模块**协作**正确 |
| L3 | **真实环境端到端**（真实浏览器、真实 HTTP 链路、真实外部依赖） | 用户路径**真的**能走通 |
| L4 | **真实生产依赖**（真实大模型、真实数据库） | 生产环境**真的**能工作 |

**规则：**

- 汇报时**必须写明你的证据处于哪一级**。
- **L3 及以下，绝不能说"功能已验证""测试通过"** —— 要说
  "在 <具体环境> 下通过 L3 验证，真实生产依赖 <xxx> 未验证"。
- **不要把 HTTP 200 当作成功。** 必须检查响应体里的**业务字段**，
  确认结果真的由预期的来源产出。
- **警惕静默降级**：很多项目在后端不可达时会切到内置 mock 数据，
  此时界面一切正常但全是假数据。测试脚本必须能证明数据来自真实链路。
- 发现环境缺失时，**如实说明**，不要用模拟环境的结果冒充真实验证。
  本项目**平台不提供模型服务**（既定方向）。但注意：BYOK「模型接入」能力
  已按评审要求**拆到 PR #4**，当前 `feature/f01-f02-intent-fix`（MVP 分支）
  **不含该功能，也不具备 L4 复现条件**；不要按旧材料以为教师端已有设置页。
  测试用的地址 / Key **绝不写进仓库任何文件或 git 历史**，只用进程环境变量临时注入。

## 4. 汇报规范

- 每个阶段结束时，用一句话给出：**做了什么 / 证据级别 / 遗留什么**。
- 发现与假设不符时**立刻停下报告**，不要将错就错继续做。
- 不要为了让测试通过而修改测试的断言；测试失败时先判断
  "是我的改动引入的"还是"既有问题"——**后者要用干净基线复现来证明**。

## 5. 收尾

完成后请提供：
1. 变更文件清单（逐个说明改了什么、为什么）
2. 验证结果（含证据级别）
3. **未验证的部分**及其补做方式
4. 提交与 PR 链接
```

## 五、每条约束的设计理由

> 写提示词时最容易犯的错：写一堆"请认真、请仔细、确保质量"——这类话**无法检查**，
> 也不会改变模型行为。下面每条都配了**可判定的形式**。

| 约束 | 为什么这样写 | 它防住的具体失败 |
|---|---|---|
| **"先只读检查并回报，之后才动手"** | 把"信息不足时的假设"逼到台面上，而不是被后续动作掩盖 | AI 拉错分支、在错误的基线上改代码、覆盖队友刚推的改动 |
| **"发现不一致要指出，不要猜测填补"** | 交接文档可能已过期，仓库才是真相 | 基于过期文档改代码，方向性错误 |
| **"只提 PR 不合并"** | 团队流程要求，人工把关 | 未经评审直接进主干 |
| **"范围外的报告而不改"** | 避免 PR 混入跨模块改动 | 一个 PR 改 5 个模块，评审成本爆炸、冲突难解 |
| **"不提交队友未跟踪产物"** | 入库时机是作者的决策 | 把别人的半成品写进主干 |
| **"不写密钥"** | 密钥一旦入库即视为泄露，需轮换 | token 泄进 Git 历史 |
| **证据分级表 + "必须注明级别"** | 让"验证到什么程度"变成**可陈述的事实** | "测试通过"——但测的是 L1 单测，却让听众以为 L4 生产可用 |
| **"HTTP 200 不等于成功"** | 很多项目失败时静默降级，状态码仍是 200 | 拿降级结果当成功汇报 |
| **"警惕静默 mock"** | 前端后端不可达时切 mock，是"界面正常但全假"的经典来源 | 在 mock 链路上宣称功能正常（本项目真实踩过） |
| **"环境缺失要如实说"** | 允许"在这台机器上做不到"，禁止"假装做到了" | 用模拟环境的结果冒充真实验证 |
| **"失败要分清是自己的还是既有的"** | 既有失败混入会让回归无法判定 | 把既有缺陷算作自己引入，或反之掩盖真实回归 |
| **"不要改断言让它变绿"** | 断言是需求的编码，改它等于改需求 | 靠削弱测试制造"全绿" |
| **踩坑清单进提示词** | 同类坑重复踩是最贵的浪费 | 本项目 14 条已踩过的坑（见交接文档第 8 节） |

## 附：设计这份提示词的三条经验

1. **初始状态比初始指令更重要。**
   一个会话开头如果已经有"已验证 / 未验证"的分级、
   "不能宣称什么"的禁令、以及一份自包含的交接文档，
   助手在后续每一步都会自动对齐；反过来，开场若只是"帮我把 F01 做了"，
   助手会在第一个岔路口就走偏。

2. **交接文档必须自包含，且必须写"不做什么"。**
   写清"被否决的方案"和"刻意不做的事"，比多写三段功能描述更能防止重复犯错。
   本项目最典型的一条：**不要从课程主题反推知识点** —— 我先做错过一次，
   后来只因为写进了交接文档，才没被下一个人再踩一遍。

3. **证据分级要写在提示词里，而不是只写"请充分测试"。**
   分级表把抽象要求变成了可回答的问题：
   *"你这次汇报的证据是 L几？"* 有了这张表，助手会主动去补齐缺口，
   而不是含糊地说"已充分测试"。
