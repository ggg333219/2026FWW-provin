## 二、本次迭代完成内容

### 2.1 Prompt 强约束体系升级（outline.py / node.py）

- **outline.py**：System Prompt 重写，新增 7 条强制约束，包括 `node_type` 枚举限制（content / section / quiz / summary / cover / divider）、禁止编造 `node_id`、字数上限 `maxLength`、禁止 `additionalProperties` 等硬性输出规范，直接压测 LLM 输出结构稳定性。
- **node.py**：三个生成方法（`_run_batch_generation` / `_run_enhanced_batch` / `generate_single`）的 System Prompt 全部重写，segment 约束细化到 `segment_type` 枚举（opening / explanation / example / interaction / transition / summary）、`estimated_seconds` 范围（15-120整数），消除生成随意性。

### 2.2 Redis 分布式锁改造（version.py）

- 全新 `_RedisLock` 类：基于 `SETNX + EX` 原子获取锁，TTL 防止持锁进程崩溃死锁，Lua 脚本原子释放（仅 token 匹配时 del），三重安全保障。
- 全新 `_DistributedLock` 双层锁：优先 Redis 分布式锁，Redis 不可用时自动降级为本地 `threading.Lock`，兼顾分布式并发与单机稳定性。
- 全部 `with lock:` 替换为 `with _DistributedLock()`，覆盖 `save_snapshot` / `list_versions` / `load_version` / `diff` / `revert_to` / `lock_version` 所有版本操作路径。

### 2.3 任务持久化异步改造（redis_client.py）

- 全新 `RedisTaskStore` 类：`save_task` / `load_task` 全部改为 `asyncio.to_thread` 异步化，持久化写入不阻塞 FastAPI 事件循环。
- 自动降级机制：Redis 连接失败（网络抖动 / 服务重启）时自动切换 `_InMemoryTaskStore`，进程不崩溃、功能不中断。
- 健康检查 `health()` 方法，返回 `{"redis": True/False, "mode": "redis"/"memory"}`，便于运维监控。

### 2.4 内容校验模块（validator.py）

- 新增 `ContentValidator` 类：`validate()` 方法计算节点内容字数 / 超标判断，`compute_scaled_font()` 根据内容体积推荐缩放字号，`paginate()` 输出分页建议。
- 接入 `main.py` Stage5 管线，在讲稿生成完成后、版本快照保存前介入校验，oversized 节点记录到版本 metadata。
- 校验结果随任务状态回写到 Redis，供前端展示"内容过长"提示。

### 2.5 normalize 函数对称性兜底（schema.py / node.py）

- `normalize_stage2_nodes`（schema.py）与 `_normalize_enhanced_scripts`（node.py）在 4 对关键字段上完全对称：`key_points ↔ core_points` 双向回退、`questions ↔ interactive_questions` 双向回退、`node_type / type` 双写、`segments / layout_hint / font_size_hint / text_alignment / slide_background` 全部存在。
- 消除"同一数据在不同阶段被不同字段名引用"导致的渲染丢失问题。

## 三、当前模块现存可发现问题 & 未完全解决的遗留隐患

### 3.1 S3 生成 LLM 调用无超时保护

**问题描述**：`LLMClient.chat_json` / `chat_with_schema` 调用时无 `timeout` 参数，LLM 服务端阻塞时 FastAPI Worker 会无限等待，极端情况导致 worker 进程夯死。

**触发条件**：调用第三方 LLM API（DeepSeek / OpenAI 等）时，若服务端响应超过 120s 未返回，进程级连接池耗尽。

**影响范围**：仅阻断 S3 生成管线，不影响预览 / 导出路径。

**当前状态**：部分缓解（`redis_client` 自动降级使任务不丢），但请求本身未释放。

### 3.2 分布式锁无死锁自动恢复

**问题描述**：持锁进程在持锁期间崩溃（Ctrl+C / OOM / 机器重启），即使 TTL 30s 后锁自动释放，但若进程在 TTL 耗尽前恢复并继续操作 `_version_locks` 字典，会出现状态不一致。

**触发条件**：WSL 重启 / 容器 OOMkill / 网络闪断导致进程非正常退出。

**当前状态**：`_RedisLock` TTL 可防护大部分场景，但本地 `_lock_for` 线程锁无 TTL 保护。

### 3.3 `questions` 字段类型冲突尚未完全验证

**问题描述**：`TeachingNode.questions` 已改为 `list[str]`，`normalize_stage2_nodes` 写出也是 `list[str]`，但 `_slide_quiz` 前端渲染器实际期望格式未与前端对齐验证（成员2侧未实测）。

**当前状态**：理论上已统一，后端规范正确；实际前端渲染是否匹配待成员2 WPS 验证时联调确认。

### 3.4 预览持久化接口路径未完全闭环

**问题描述**：本人虽在 `validator.py` 接入管线时确认了快照保存路径，但 `GET /api/v1/gen/preview/{gen_id}` 接口由成员2负责，当前 Redis 恢复路径与磁盘快照路径的合并逻辑存在边界条件：若 Redis 有数据但节点内容为空（半持久化状态），接口会返回空数据而非回退到磁盘快照。

**当前状态**：理论路径存在，实际未联调。

### 3.5 `ContentValidator` 分页建议未反馈至模板渲染

**问题描述**：`validator.paginate()` 输出分页建议，但目前仅写入版本 metadata，未联动 `preview.py` 或 `export_ppt.py` 的实际渲染逻辑，oversized 节点的分页建议属于"写了但没用上"。

## 五、后续可优化方案 & 迭代建议

### 5.1 LLM 超时保护方案

**问题对应**：3.1

**优化思路**：所有 `LLMClient` 调用统一增加 `timeout=120` 参数（aiohttp / requests 均支持），同时在 `NodeGenerator` 层增加重试逻辑（最多 1 次重试，指数退避 2s / 4s）。

**技术方案**：

```python
# ai_engine/core/llm.py 改动
result = self._client.chat_with_schema(
    ..., timeout=aiohttp.ClientTimeout(total=120)
)
```

**预期收益**：消除 worker 进程夯死风险，S3 生成失败可自动重试，用户感知为"生成稍慢"而非"页面卡死"。

---

### 5.2 分布式锁死锁自动恢复方案

**问题对应**：3.2

**优化思路**：在 `_DistributedLock` 构造时记录进程 PID，持有本地线程锁时若检测到 PID 变化（进程被替换），强制释放并重新获取。

**技术方案**：

```python
class _DistributedLock:
    def __enter__(self):
        pid = os.getpid()
        if self._llock_pid != pid:
            # 进程重启，强制重置本地锁
            self._llock_pid = pid
            self._llock = _lock_for(self._gen_id)
```

**预期收益**：持锁进程崩溃重启后，下一次版本操作可正常获取锁，不会因为旧 PID 残留导致永久阻塞。

### 5.3 前后端 `questions` 格式对齐验证方案

**优化思路**：由成员2负责，在 WPS 验证报告中实测 `_slide_quiz` 对 `list[str]` 的渲染是否正常；如异常则在 `preview.py` 的 quiz 渲染分支增加 `json.dumps` 或模板格式兼容。

questions = node.get("questions", [])

**预期收益**：彻底消除类型歧义，quiz 节点在预览和 WPS 导出两端行为一致。

### 5.4 预览持久化接口边界条件修复方案

**问题对应**：3.4

**优化思路**：在 `get_preview` 接口中，若 Redis 数据存在但 `nodes` 为空，主动回退查询磁盘快照，而非直接返回 404。

**技术方案**（成员2实施）：

```python
if task and not nodes:
    # Redis 有记录但节点为空，降级到磁盘快照
    vm = get_version_manager()
    snap = vm.load_version(gen_id, version)
    if snap:
        nodes = [n.model_dump(mode='json') for n in snap.nodes_snapshot]
```

**预期收益**：消除半持久化状态的边界盲区，刷新页面100%能恢复预览。

## 六、本次开发总结

### 6.1 开发难点

**难点一：多成员 Schema 博弈**
`TeachingNode` 的字段定义分散在成员1（schema.py）和成员4（core/schema.py）两个位置，`questions` 类型、字段名混用（`core_points` vs `key_points`、`interactive_questions` vs `questions`）等问题贯穿全程，本人最终以 normalize 双写兜底方式化解歧义，而非强制统一某一版本。

**难点二：Redis 降级与线程锁的并发安全问题**
`_DistributedLock` 设计初期未考虑进程 PID 变化场景，TTL 机制虽能防护大部分崩溃场景，但本地线程锁的持有状态与进程生命周期绑定，WSL 重启场景下存在理论死锁窗口。该问题已在 5.2 给出方案但本轮未实施。

**难点三：Mock 测试环境与真实 LLM 的差异**
无 API Key 时所有 LLM 调用走 fallback 兜底，无法真实验证 Prompt 约束是否有效触发。7条强约束的 Prompt 改造效果依赖真实 LLM 调用才能验证，当前属于"结构正确、效果待验"状态。

### 6.2 主要收获

- **Pipeline 串联思维**：理解了 S1（切片）→ S2（大纲）→ S3（生成）→ S4（导出）→ S5（校验）的完整管线依赖关系，任何一个环节的 Schema 变动都可能产生跨端影响。
- **分布式一致性设计**：Redis SETNX + TTL + Lua 释放的三段式分布式锁设计，是对教科书式"悲观锁"的工程化落地；降级机制比单一实现更具生产级可靠性。
- **与其他模块的联动**：成员的 schema.py 改动直接影响了本人在 node.py 的 `_normalize_enhanced_scripts` 字段映射逻辑，说明"模块解耦"在快速迭代中需要持续校准。

### 6.3 卡点与对接情况

| 卡点 | 根因 | 结果 |
|------|------|------|
| `questions` 类型在 schema.py 仍为 `list[dict]` | 成员1首次修改时未同步前端渲染期望 | 已修复为 `list[str]` |
| 前端 `_slide_quiz` 渲染格式未知 | 前端代码未同步给后端成员 | 成员2承诺 WPS 验证时联调 |
| MinIO 真实上传链路未验 | 成员3测试环境缺失 | `minio_client.upload_file` 代码已存在，待实测 |

### 6.4 整体评价

本次迭代成员4的工作覆盖了 S3 生成管线的"稳定性底座"建设：Prompt 约束消除 LLM 随机性、分布式锁保障并发安全、异步持久化保障任务不丢、normalize 对称性消除字段歧义。核心管线已具备生产可用性，但全链路端到端演示仍依赖成员2的预览接口闭环和成员3的 WPS 实测完成。
