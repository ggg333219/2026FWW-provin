# 当前状态与痛点

## 现有架构概览

```
S1IntentPage  ──→  S2MaterialPage  ──→  S3StudioPage  ──→  S4VersionPage
     │                    │                   │                   │
     ▼                    ▼                   ▼                   ▼
intentStore          materialStore       generationStore      versionStore
     │                    │                   │                   │
     │    ❌ 无自动透传    │    ❌ 无自动透传   │    ❌ 无自动透传   │
     └────────────────────┴───────────────────┴───────────────────┘
```

## 4 个断裂点

### 断裂点 1：S1 → S2 意图数据丢失

**现状**：用户在 S1IntentPage 的 TeacherIntentPanel 中完成了意图解析，`intentStore.parsedIntent` 有完整数据（topic、subject、learningObjectives 等）。但跳转到 S2MaterialPage 后，S2MaterialWorkspace 的 KnowledgeBasePanel 搜索框为空，用户需要手动输入搜索关键词。

**影响**：用户体验割裂，需要重复输入已在 S1 确认过的内容。

**修复方案**：S1 在 intentStore.parsedIntent 变化时写入 localStorage 特定 key，S2 在挂载时从该 key 读取并预填搜索框。

**涉及文件**：
- `frontend/teacher/src/pages/S1IntentPage.vue`
- `frontend/teacher/src/components/teacher/S2MaterialWorkspace.vue`
- `frontend/teacher/src/components/teacher/KnowledgeBasePanel.vue`

**工作量**：约 1 人天

---

### 断裂点 2：S2 → S3 证据未传递

**现状**：S2MaterialWorkspace 的 KnowledgeBasePanel 通过 RAG 检索生成了 `evidencePackets`，`materialStore.s3EvidencePayload` getter 能返回符合后端契约格式的证据包。但 S3StudioPage 调用的 `teacherV1Api.coursewares.generateScript()` 只接收 `{ courseId, pageNum, mode }`，没有证据上下文字段。

**影响**：AI 生成课件时缺乏教学资料上下文，生成结果与 S2 准备的资料脱节。

**修复方案**：扩展 generateScript API 以接受 `evidence` 参数，或通过 localStorage 传递证据。S3 在调用 AI 生成前从 materialStore 读取证据包并附加到请求中。

**涉及文件**：
- `frontend/teacher/src/services/v1/generationApi.js`
- `frontend/teacher/src/pages/S3StudioPage.vue`
- `frontend/teacher/src/stores/materialStore.js`

**工作量**：约 1.5 人天

---

### 断裂点 3：S3 → S4 gen_id 未传递

**现状**：S3StudioPage 在生成完成后从后端获得 `gen_id`（生成会话 ID），但 `generationStore` 没有字段存储它。S4VersionPage 的 `genIdInput` 初始值来自 `workspaceStore.currentCourseId`，不是 S3 的 `gen_id`。

**影响**：用户需要在 S4 手动输入 gen_id 才能查看版本历史，流程被打断。

**修复方案**：在 generationStore 中增加 `lastGenId` 字段，S3 生成完成后写入。S4 从 generationStore 读取（或 localStorage 缓存）自动填充。

**涉及文件**：
- `frontend/teacher/src/stores/generationStore.js`
- `frontend/teacher/src/pages/S3StudioPage.vue`
- `frontend/teacher/src/pages/S4VersionPage.vue`

**工作量**：约 0.5 人天

---

### 断裂点 4：WorkspacePage 多 Store 未编排

**现状**：WorkspacePage 集成了所有 4 个 Skill 的 Tab（intent、material、script、version），但 Tab 之间没有数据联动——在 intent Tab 确认意图后切到 material Tab，不会自动填充搜索；在 script Tab 生成后切到 version Tab，不会自动填入 gen_id。

**影响**：在同一页面内使用 Tab 切换时，用户仍然需要手动传递上下文。

**修复方案**：在 WorkspacePage 中添加 Vue watchers，监听关键 Store 变化并同步到其他 Store 或 localStorage。

**涉及文件**：
- `frontend/teacher/src/pages/WorkspacePage.vue`

**工作量**：约 1 人天

## 技术选型理由

选择 **localStorage 作为主要透传媒介**，而非直接用 Pinia store 跨页面引用，原因：

1. **刷新不丢失** — 路由页面刷新后 Store 重置，但 localStorage 持久
2. **解耦模块** — 每个成员不需要直接引用别人的 Store
3. **渐进式增强** — 先实现最基本的透传，后续可升级为 Store-to-Store 联动
4. **与现有模式一致** — S2MaterialWorkspace 已使用 localStorage 保存 `fuww_s2_current_node_ref`、`fuww_s2_bound_evidence` 等

## 统一 Key 命名规范

```
fuww_intent_parsed          → S1 intentStore.parsedIntent 的 JSON 序列化
fuww_s2_evidence_packet     → materialStore 的最新证据包
fuww_last_gen_id            → generationStore 的最新 gen_id
fuww_s2_current_node_ref    → [已有] S2 当前节点引用
fuww_s2_bound_evidence      → [已有] S2 已绑定证据
fuww_s2_selected_materials  → [已有] S2 已选素材
fuww_s2_session_id          → [已有] S2 会话 ID
fuww_mock_mode              → [已有] Mock 模式标志
```
