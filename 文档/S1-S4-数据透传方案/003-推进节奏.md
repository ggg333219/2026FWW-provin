# 推进节奏

建议按"先单点透传、后全局编排"的顺序迭代，避免互相等待。

## 总周期：3~4 天

## Stage 1：契约冻结与前置准备（半天）

全员参与，统一以下契约：

- localStorage key 命名：`fuww_intent_parsed`、`fuww_s2_evidence_packet`、`fuww_last_gen_id`
- 各透传数据的 JSON Schema（字段名、类型、可选/必填）
- 涉及 API 扩展的字段名（generationApi.js 的 evidence 参数格式）
- 确认各自要修改的文件，避免冲突

**产出**：以上契约文档化到 `001-当前状态与痛点.md` 中。

---

## Stage 2：成员 A / B / C 并行开发（1.5 天）

三位成员独立开发，互不依赖：

### 成员 A（S1 → S2）
- 半天：S1IntentPage 添加 watcher + localStorage 写入
- 半天：KnowledgeBasePanel 添加 mounted 读取 + 预填逻辑
- 验收：手动验证 S1 → S2 跳转后搜索框自动填充

### 成员 B（S2 → S3）
- 半天：generationApi.js 扩展 evidence 参数
- 半天：S3StudioPage 集成证据读取 + 传入
- 验收：手动验证 S3 生成请求携带证据参数

### 成员 C（S3 → S4）
- 0.5 天：generationStore 增加 lastGenId 字段 + 写入逻辑
- 0.5 天：S3StudioPage 写入 lastGenId + S4VersionPage 读取自动填充
- 验收：手动验证 S3 → S4 跳转后 gen_id 自动填入

---

## Stage 3：成员 D 全局编排 + 联调（1.5 天）

### 成员 D（WorkspacePage 跨 Store 编排）
- 1 天：添加 watcher，监听 4 个 Store 的出口数据变化
- 0.5 天：处理 Tab 切换时的数据同步，确保刷新后不丢失

### 联调
- 全员一起走一遍完整流程：S1 → S2 → S3 → S4
- 确认每条数据透传链路正确
- 修复边界情况（空数据、异步加载时序、错误处理）

---

## Stage 4：润色与收尾（0.5 天）

- 清除调试日志
- 确认所有页面刷新不丢状态
- 确认 mock 模式下也能正常透传
- 完成演示所需的完整流程
